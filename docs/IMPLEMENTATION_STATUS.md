# Implementation status

Baseline date: 2026-08-14. Release candidate: `0.2.0`.

## Current capabilities

- **MV3 Edge extension — Implemented.** Desktop Edge side panel, service worker, and all-frame content sensors.
- **Hosted iPhone workspace — Deployed, physically verified, and reproducible.** The owner-authenticated responsive workspace works while the Mac is off, displays the enrolled desktop device, and is source-controlled in `apps/owner-workspace`. Sites version 10 was deployed from the verified source commit recorded in `docs/OWNER_WORKSPACE.md`.
- **Hosted workspace status and profile model — Implemented.** The deployed workspace uses autosave with manual sync as fallback, exact cloud version acknowledgements, canonical repeatable records, confirmed deletion tombstones, fail-closed payload parsing, protected cross-device conflict choices, and active application review state.
- **End-to-end encrypted sync — Implemented.** Owner-held AES-256-GCM key with ciphertext profile, résumé, application, and review events.
- **Device enrollment/revocation — Implemented.** Ten-minute single-use pairing, P-256 proof, scoped credential, and owner revocation.
- **Recovery — Implemented; owner drill pending.** Recovery-key export/import exists; the server cannot recover plaintext or the owner key. A synthetic fresh-client recovery drill remains a release gate before full real private-data migration.
- **Universal DOM/ARIA discovery — Expanded.** Native controls, generic comboboxes, injectable frames, open Shadow DOM, stable control fingerprints, dynamic rescanning, and controlled ARIA-combobox option discovery.
- **Dynamic observation — Implemented.** Debounced mutation rescans, semantic-attribute changes, form input/change signals, and History API navigation listeners.
- **Semantic ontology — Expanded deterministic implementation.** Identity, contact, address, education, employment, authorization, sponsorship, preference, and protected/high-risk concepts plus `UNKNOWN`. Explicit current sponsorship and future sponsorship are distinct; ambiguous generic sponsorship remains manual.
- **Protected profile — Implemented across desktop and hosted clients.** Structured identity, contact, address, authorization, sponsorship, and preference facts use deliberate protected confirmation. Repeatable education/employment/project/certification/language records have durable SQLite storage, browser/cloud contracts, stable order, explicit tombstones, and full editors on both surfaces.
- **Profile persistence — Implemented with autosave and convergence safety.** Ordinary facts debounce-save; protected facts confirm deliberately; stale in-flight saves cannot mark newer edits synchronized; protected cross-device conflicts do not silently last-write-win.
- **Résumé vault — Strengthened.** Client-side encrypted PDF/DOC/DOCX uploads are size/type validated. New uploads record SHA-256 of the original bytes plus family/version/source metadata, and application reviews record the selected résumé hash when available so the exact selected bytes can be identified. Existing legacy résumé records remain readable.
- **Deterministic pre-flight resolver — Implemented and wired into the desktop UI.** A central resolver returns `READY`, `REVIEW`, or `UNRESOLVED`; missing or unmapped facts are not invented, generated/non-authoritative facts cannot become ready answers, and protected/sensitive/high-risk facts require review.
- **Pre-flight policy layer — Implemented foundation.** Trusted contradiction detection, explicit-only knockout rules, salary-range comparison that never auto-rejects, and a gate that allows action only when every item is `READY` are covered by tests. Employer/job-specific knockout-rule extraction is not yet automated.
- **Review backlog model — Implemented as a shared contract.** Current review work is scoped to active application pages and latest review state, preventing historical discovered questions from being presented as current unresolved work. The hosted source and deployed UI consume the same active application/review entities.
- **Guarded fill — Implemented for supported controls.** Approved native text, textarea, select, radio, checkbox, contenteditable, and open-Shadow-DOM controls are filled only when supported and verified through the DOM afterward. Radio groups are value-aware. Ambiguous checkbox values fail without changing the page.
- **Controlled ARIA combobox fill — Implemented safe subset.** MUNSHI considers only options explicitly owned through `aria-controls`/`aria-owns`, selects only an exact already-present option, verifies committed state/value, and restores the original input on failure. Async autocomplete/date/multi-select widgets remain future interaction-recipe/state-wait work.
- **Employer file controls — Owner-controlled verified handoff.** The encrypted résumé vault does not imply automatic employer file upload. MUNSHI can request the employer picker, provides an on-page direct-gesture fallback when Edge blocks a cross-context picker request, and locally fingerprints the owner-selected file for résumé-binding verification. Operating-system file selection remains an owner action.
- **Final submission — Manual safety checkpoint.** No automatic final submit, CAPTCHA, MFA, OTP, identity-verification, or security-checkpoint bypass.
- **Evidence graph/retrieval — Implemented foundation with durable storage.** Evidence nodes/edges, trust-aware bounded retrieval, protected-evidence exclusion by default, generated-text exclusion from authoritative retrieval, contradiction-edge detection, and SQLite persistence exist.
- **Evidence context and generated-draft validation — Implemented foundation.** Bounded context assembly does not partially slice evidence records. Generated drafts require structured claims, claim-to-evidence IDs available in the supplied context, contradiction checks, and optional word-limit validation. Résumé/document parsing into evidence nodes still needs implementation.
- **AI budget/pricing router — Implemented deterministic foundation.** Explicit owner/configured model pricing is required; no provider price is silently hard-coded. Pre-request budget decisions can allow, warn, or hard-stop before spend, and AI usage has a durable SQLite ledger. The router refuses generation when context/pricing/budget gates are missing or stale.
- **OpenAI provider adapter — Implemented behind a disabled inference boundary.** The native adapter targets the Responses API, sets `store: false`, sends only bounded caller-supplied evidence context, requests strict JSON-schema claim/evidence output, requires completed/non-refusal responses and token usage, and enforces a local output-token ceiling. It is not wired to a user-facing generation command, and no real API request/spend has been performed.
- **OpenAI configuration — Secure configuration foundation implemented.** Keychain storage, key removal, connection testing, model discovery, and local model/budget controls. Non-secret AI preferences are backed up under `settings/`. The Keychain write path no longer places the plaintext API key in process arguments; a physical Mac Keychain smoke test remains before using a real key.
- **AutoPilot guarded runtime — Implemented and live in the desktop extension.** Start, Pause, Resume, and Stop are backed by a persistent Observe → Plan → Act → Verify → Rescan controller. It executes one approved visible fill at a time, verifies the DOM after every fill, supports safe-progress fills before review-only items, persists checkpoints before navigation and owner pauses, recovers durable application state, and never performs final employer submission or security-checkpoint actions. Physical ATS crash/interruption and broader site-compatibility testing remain release work.
- **Progressive learning — Implemented foundation with durable storage.** Structural component fingerprints, shadow interaction recipes, verified-only attempt metrics, promotion thresholds, and rollback after configured consecutive verified failures exist. Migration `004` and the native learning/analytics store persist recipes and attempts. Recipe actions do not include final submit or security bypass. Live capture/execution and Teach-MUNSHI remain future work.
- **Analytics/experiments — Implemented foundation with durable storage.** Application outcomes, opaque attribution tokens, deterministic salted experiment assignment, experiment variants/assignments, and minimum-sample statistical-honesty gates exist. The system does not label an undersampled variant a winner and does not imply causality from descriptive rates. Production exports/UI and portfolio-event ingestion remain future work.
- **Native companion — Expanded verified foundation.** SQLite, migrations `001`–`005`, Native Messaging, transactional outbox, backups, runtime verification, Keychain credential operations, canonical profile snapshots, evidence/checkpoint/usage persistence, and learning/analytics persistence are covered by native/migration CI.
- **n8n — Optional signed bridge only.** HMAC event bridge exists with no dependency for the core workflow; production orchestration workflows are not configured.
- **AI inference/generated responses — Still disabled.** Even though provider, router, context, budget, usage, and structured validation foundations now exist, the extension/native protocol does not expose a normal generated-answer command. End-to-end evidence parsing, pricing governance, physical provider smoke tests, review UX, and final validation gates remain before enabling inference.

## Hosted workspace release boundary

The hosted workspace source is tracked in `apps/owner-workspace`, has its own dependency lock and CI job, and is deployed from an exact source commit through the Sites version boundary. Its status contract makes manual sync a fallback, validates exact optimistic-concurrency acknowledgements, distinguishes resolved history from active conflicts, and calculates overview state from one synchronized authority snapshot. Production access remains owner-only.

## AI boundary

MUNSHI now has a provider adapter, explicit pricing/budget router, evidence context, claim/evidence validation, usage ledger, and durable evidence storage, but generated application answers remain intentionally disabled at the extension/native messaging boundary. The API key remains local to the Mac and is never returned by native status calls. No provider request should be made until a physical Mac Keychain smoke test passes, explicit current pricing is configured, budget policy is verified, synthetic evidence parsing/context is proven end to end, and the owner separately chooses to configure a real provider credential.

## iPhone boundary

The iPhone workflow intentionally uses the hosted workspace because Edge on iOS does not provide the general desktop extension APIs needed to inspect or fill arbitrary employer pages. A paired desktop Edge installation performs those page-bound actions; the iPhone performs the private-data, résumé, review, approval, device, and recovery workflow independently of the Mac.
